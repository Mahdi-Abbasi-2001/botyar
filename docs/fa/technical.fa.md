# بات‌یار — مستندات فنی و زیرساخت

**نسخهٔ آنلاین:** https://botyar.liara.run · **ربات مشترک بله:** `@botyar_ai_bot` · **مخزن کد:** github.com/Mahdi-Abbasi-2001/botyar

این سند برای داوران نوشته شده است و هر چیزی که می‌گوید در کد همین مخزن وجود دارد. مواردی که ساخته شده‌اند اما هنوز روی پیام‌رسان واقعی آزموده نشده‌اند، صریحاً با عبارت **«آزموده‌نشده روی پیام‌رسان واقعی»** مشخص شده‌اند (بخش ۱۲).

## ۱. محصول در یک نگاه

صاحب کسب‌وکار ربات خودش را به فارسی توضیح می‌دهد. ایجنت ابهام‌ها را می‌پرسد، ربات را به‌صورت یک توصیف ساختاریافته و اعتبارسنجی‌شده (**BotSpec**) می‌سازد، برایش سناریوهای تست می‌نویسد و روی موتور واقعی اجرا می‌کند، خطاها را اصلاح می‌کند و فقط وقتی همهٔ تست‌ها سبز باشند اجازهٔ انتشار می‌دهد. مشتری‌ها روی بله یا تلگرام فقط با یک **موتور قطعی (deterministic)** حرف می‌زنند که همان BotSpec را اجرا می‌کند. صاحب کسب‌وکار پنل دارد (ثبت‌ها، پیام‌ها، اطلاعیه‌ها، مشتری‌ها، فایل‌ها) و هر تغییری را با یک جمله درخواست می‌کند؛ تغییر با نمایش تفاوت و اجرای دوبارهٔ همهٔ تست‌های قبلی اعمال می‌شود.

پنج اصل طراحی که در کد اِعمال شده‌اند (فقط شعار نیستند):

1. **ایجنت هرگز کد نمی‌نویسد.** خروجی ایجنت یک BotSpec است (مدل‌های Pydantic در `api/app/spec.py`) و یک موتور ثابت آن را اجرا می‌کند. پس ربات ساخته‌شده نمی‌تواند کد مخرب یا غیرقابل‌بررسی داشته باشد.
2. **مشتری هرگز با مدل زبانی حرف نمی‌زند.** در زمان اجرای ربات هیچ فراخوانی LLM وجود ندارد؛ هزینهٔ هر پیام مشتری عملاً صفر است و تزریق پرامپت (prompt injection) از طریق چت ممکن نیست. (تنها استفادهٔ هوشمند در زمان مشتری، یک جست‌وجوی embedding برای بخش «پرسش‌های متداول» است که فقط می‌تواند جملات خود صاحب کسب‌وکار را برگرداند، چیزی تولید نمی‌کند، و با قطع شدن سرویس به تطبیق ساده‌ی کلمات برمی‌گردد.)
3. **نسخه‌ای که تستش رد شود منتشر نمی‌شود.** قفل انتشار هم در رابط کاربری و هم در سرور اِعمال می‌شود.
4. **ارزان بودن از ساختار می‌آید.** یک مدل برای همهٔ مراحل ایجنت، با سطح استدلال تنظیم‌شده برای هر مرحله، و ثبت هزینهٔ هر فراخوانی؛ هزینهٔ اندازه‌گیری‌شدهٔ ساخت یک ربات به‌طور میانگین حدود **۰٫۰۰۲ دلار** است (بخش ۹).
5. **برای مشتری باز، برای پول بسته.** اشتباهات راه‌اندازی (مثلاً عدم دسترسی ربات به کانال) هیچ‌وقت مشتری را قفل نمی‌کنند؛ اما پرداخت فقط وقتی ثبت می‌شود که خود پیام‌رسان آن را تأیید کند.

## ۲. معماری

```
 Owner browser --> Next.js UI (static export) --> FastAPI (single instance) --> PostgreSQL (SQLite in dev)
                                                       |
        +----------------------------------------------+------------------------------+
        v                                              v                              v
 BUILDER AGENT (LangGraph)                  RUNTIME ENGINE (no LLM)           BACKGROUND JOBS (1 thread)
 clarify > design > validate >              engine.handle(spec, session,      reminders, scheduled announcements,
 write_tests > run_tests >                  text, store) -> actions           unpaid-order expiry, anon-chat queue,
 repair (max 3) > save version                      ^                         outbox retries, webhook refresh
        |                                           | webhooks
        v                                   +-------+--------+
   OpenAI API                          Bale Bot API      Telegram (via a Deno relay outside Iran)
```

| لایه | فناوری |
|---|---|
| رابط کاربری | Next.js (خروجی ایستا)، RTL فارسی، فونت وزیرمتن، Tailwind 4؛ FastAPI آن را از `api/static` و روی همان origin سرو می‌کند |
| سرور | Python 3.12، FastAPI، SQLAlchemy 2، Pydantic 2، httpx |
| ایجنت | LangGraph؛ OpenAI Responses API با خروجی ساختاریافتهٔ strict؛ مدل `gpt-6-luna` |
| جست‌وجوی معنایی | `text-embedding-3-small` (فقط برای پرسش‌های متداول) |
| دیتابیس | PostgreSQL روی لیارا (SQLite برای توسعه و تست) |
| میزبانی | لیارا (Docker، پلن small-g2، یک نمونه)؛ رلهٔ تلگرام روی Deno Deploy |
| پیام‌رسان‌ها | Bale Bot API (`tapi.bale.ai`) و Telegram Bot API از طریق رله |
| کتابخانه‌های دیگر | PyMuPDF (PDF)، openpyxl (Excel)، Pillow (اعتبارسنجی تصویر)، numpy، cryptography، bcrypt، PyJWT |

حجم کد: حدود ۱۱٬۵۰۰ خط Python در `api/app`، حدود ۵٬۶۰۰ خط TypeScript/TSX در `web`، ۴۹۱ تست خودکار، ۶۸ سناریوی ارزیابی ایجنت و ۹۹ عملیات API.

## ۳. BotSpec: زبان مشترک ایجنت و موتور

```
BotSpec { name, welcome, menu[{label, block}], blocks[...], gate? }
```

| بلوک | تجربهٔ مشتری | نکته‌ها |
|---|---|---|
| `message` | متن؛ متن‌های تصادفی متناوب، عکس/فایل/آلبوم، موقعیت روی نقشه، کارت تماس، ساعت کاری با «الان باز/بسته‌ایم»، دکمهٔ لینک | **قفل عضویت (`join`)**: محتوا فقط پس از عضویت در ۱ تا ۵ کانال ارسال می‌شود؛ هر محتوا لینک اختصاصی خودش را دارد |
| `form` | پرسیدن مرحله‌به‌مرحله (متن، موبایل ایرانی، عدد، انتخاب، چندانتخابی، تاریخ، موقعیت، فایل) | شرط نمایش، مرور پیش از ثبت، پذیرش/رد از پنل، ذخیرهٔ مشخصات برای دفعهٔ بعد |
| `booking` | زمان‌های ثابت با ظرفیت و لیست انتظار (با جایگاه در صف)؛ **جلسه‌های تاریخ‌دار** (مثلاً ۴ جلسهٔ کارگاه با تاریخ شمسی؛ ظرفیت هر جلسه جدا، پس از شروع پنهان می‌شود)؛ **یک نفر دو بار یک جای یکسان را نمی‌گیرد**؛ کلاس‌های هفتگی با تاریخ شمسی؛ **نوبت‌دهی از روی ساعت کاری** (کارشناس، خدمت، مدت، استراحت)؛ لغو با مهلت؛ **تغییر زمان**؛ یادآوری | هم‌زمانی با قفل هر ربات امن است |
| `catalog_order` | فروشگاه با فهرست داخل ربات یا **جدول محصولات** (دسته، جست‌وجو، صفحه‌بندی، گزینه‌ها، موجودی، عکس)، سبد، تحویل (هزینه و مناطق)، **کد تخفیف**، پرداخت آنلاین بله یا کارت‌به‌کارت | وضعیت سفارش از پنل: جدید ← در حال آماده‌سازی ← آماده ← تحویل |
| `faq` | انتخاب سؤال یا نوشتن آزاد؛ پاسخ همیشه متن خود صاحب کسب‌وکار است | سه سطح اطمینان؛ سؤال‌های بی‌پاسخ ثبت می‌شوند |
| `contact` | پیام به صاحب کسب‌وکار با موضوع؛ پاسخ از پنل به چت مشتری می‌رسد | صندوق پیام |
| `feedback` | امتیاز ۱ تا ۵ بر حسب جنبه + توضیح؛ تماس‌گرفتن با امتیاز پایین | امتیاز خودکار پس از مراجعه |
| `menu` | زیرمنو تودرتو | بدون حلقه |
| `quiz` | آزمون چهارگزینه‌ای یا شخصیت‌سنجی؛ نمرهٔ قبولی، کد تخفیف برای قبول‌شدگان، **تاریخچهٔ «نتیجه‌های من»**، **بانک سؤال (تا ۵۰۰ سؤال)** | بانک: افزودن دستی، وارد کردن Excel/CSV/متن/عکس/PDF، **ساخت از روی موضوع** |
| `referral` | لینک دعوت شخصی، شمارش، هدف و پاداش | فقط مشتری کاملاً تازه شمرده می‌شود |
| `anon_chat` | چت ناشناس بین دو مشتری | فیلتر لینک و شماره، گزارش و مسدودسازی |
| `admin_notify` | (سمت صاحب) اطلاع به او پس از تکمیل یک بلوک | شرط حداقل مبلغ/حداکثر امتیاز |
| `gate` (سطح ربات) | عضویت اجباری در کانال پیش از هر کاری | ربات باید مدیر کانال باشد |

اعتبارسنجی (Pydantic): شناسه‌ها یکتا؛ هدف منو موجود؛ `admin_notify` بلوک موجود را زیر نظر دارد؛ زیرمنوها حلقه نمی‌سازند؛ جانگهدارهای متن تأیید باید به فیلد واقعی اشاره کنند (تا یک `{typo}` هیچ‌وقت به مشتری نرسد)؛ کد تخفیف‌ها یکتا هستند. طرح‌واره‌ای که به مدل داده می‌شود (`llm_schema.py`) همین قواعد را با union ساده بازتاب می‌دهد، چون خروجی ساختاریافتهٔ strict از `oneOf` پشتیبانی نمی‌کند.

## ۴. موتور اجرا

`engine.handle(spec, session, text, store, now, matcher, rng, clicked) -> list[action]`

- **خروجی** فهرستی از actionهاست: `send {text, buttons, edit}`، `notify_admin`، `notify_customer`، `notify_staff`، `media`، `location`، `contact`، `invoice` و `anon_*`. لایهٔ پیام‌رسان آن‌ها را به فراخوان API تبدیل می‌کند؛ شبیه‌ساز وب و اجراکنندهٔ تست‌ها دقیقاً همین فهرست را مصرف می‌کنند، یعنی آنچه تست می‌شود همان چیزی است که مشتری می‌بیند.
- **ویرایش پیام در جا:** وقتی مشتری دکمه‌ای را می‌زند، پاسخ به‌جای پیام جدید، همان پیام را ویرایش می‌کند (منو ← صفحه ← «بازگشت به منو» همه در یک پیام). پاسخ‌هایی که یک کار را تمام می‌کنند (تأیید ثبت، لغو، نتیجه) یا عکس/موقعیت/فاکتور دارند پیام جدید می‌مانند. تایپ مشتری همیشه پیام جدید می‌گیرد.
- **بازگشت به منو:** موتور خودش به هر صفحه‌ای که دکمهٔ انتخاب دارد و راه خروج ندارد «بازگشت به منو» اضافه می‌کند (به‌جز پرسش‌های بله/خیر)؛ هیچ مسیری مشتری را گیر نمی‌اندازد. یک ابزار بازرسی با گفت‌وگوهای تصادفی روی همهٔ انواع بلوک این را بررسی کرده است.
- **نشست‌ها** JSON هستند و کپی عمیق می‌شوند؛ اگر صاحب کسب‌وکار وسط گفت‌وگوی مشتری ربات را دوباره منتشر کند و وضعیت ذخیره‌شده به چیزی که دیگر نیست اشاره کند، موتور مشتری را با توضیح به منو برمی‌گرداند.
- **قطعی بودن:** ساعت قابل تزریق است؛ تست‌های ایجنت روی یک ساعت ثابت (شنبه ۱۴۰۵/۰۷/۱۱، ساعت ۱۲) اجرا می‌شوند و متن‌های تصادفی در تست به ترتیب چرخشی می‌آیند.
- **دادهٔ دکمه** ASCII و حداکثر ۶۴ بایت است؛ ارقام فارسی فقط در لایهٔ نمایش جایگزین می‌شوند تا منطق و تست‌ها ساده بمانند.
- **ورودی‌های خصمانه:** `test_fuzz.py` هزاران گفت‌وگوی تصادفی و بدخواهانه را روی ربات‌ها اجرا می‌کند و پایداری‌ها را می‌سنجد: ظرفیت هیچ‌وقت رد نمی‌شود، موجودی منفی نمی‌شود، وضعیت همیشه قابل ذخیره است.

## ۵. جریان اجرای ایجنت

ایجنت یک گراف LangGraph است: `clarify → design → validate → write_tests → run_tests → repair (حداکثر ۳ بار) → save`. نتایج ممکن: `done`، `needs_input` (حداکثر سه پرسش کوتاه فارسی)، `failed`، `declined`.

1. **clarify (روشن‌سازی):** تصمیم می‌گیرد بسازد، بپرسد یا (فقط وقتی هیچ بخش مفیدی ممکن نیست) رد کند. در دور اول یک ربات تازه، یک پرسش پیشنهادی می‌پرسد که بسته به نوع کسب‌وکار قابلیت‌های طبیعی را پیشنهاد می‌کند (فروشگاه: پرداخت، تحویل، کد تخفیف؛ نوبت‌دهی: یادآوری، مهلت لغو؛ …) و آنچه صاحب کسب‌وکار از قبل گفته را دوباره نمی‌پرسد. در درخواست تغییر فقط وقتی می‌پرسد که یک واقعیت لازم کم باشد (مختصات نقشه، شمارهٔ کارت، @نام کانال). قواعد پرامپت: هیچ واقعیتی (قیمت، ساعت، مختصات، پاسخ آزمون، نام کانال) را از خودش نمی‌سازد؛ بخش پشتیبانی‌نشده را با عبارت «پشتیبانی نمی‌شود» اعلام می‌کند و نزدیک‌ترین ربات ممکن را می‌سازد.
2. **design (طراحی):** کل BotSpec را با خروجی ساختاریافتهٔ strict برمی‌گرداند؛ خطای Pydantic به مدل برمی‌گردد (حداکثر ۳ تلاش). پس از طراحی، **پوشش‌های قطعی (بدون مدل)** اجرا می‌شوند: واقعیت‌هایی که صاحب کسب‌وکار صریحاً داده (ساعت مثل ۱۶:۳۰، تاریخ شمسی، شماره تلفن، شمارهٔ کارت، @کانال، لینک) باید جایی در ربات باشند؛ مدت نوبت دقیقاً همان دقیقه‌ای باشد که گفته شده؛ «شنبه تا چهارشنبه» همهٔ روزهای میانی را داشته باشد؛ ارسال رایگان بدون هزینهٔ ارسال بی‌معنی نباشد؛ هیچ متنِ مشتری دستورالعملِ صاحب‌ربات («اینجا وارد کنید») نداشته باشد؛ آزمون شخصیت‌سنجی به‌اندازهٔ `pick` سؤال داشته باشد؛ هر فرم، نوبت‌دهی، سفارش و پیام به مدیر اعلان صاحب‌ربات داشته باشد؛ دعوت دوستانی که «تخفیف» وعده می‌دهد کد تخفیف واقعی (`reward_code`) و همان تعداد دوستی را داشته باشد که صاحب کسب‌وکار گفته؛ هیچ پیامی برای مشتری فقط اعلام نکند که ربات فلان کار را نمی‌کند؛ شمارهٔ تلفن در متن پیام بیاید و کارت تماس جداگانه فقط وقتی ساخته شود که صاحب کسب‌وکار «تماس با یک لمس» خواسته باشد؛ در «فرض‌ها» قابلیتی (نظرسنجی، یادآوری) ادعا نشود که در ربات نیست؛ و در بقیه‌ی موارد: نام‌های رزروشدهٔ دکمه‌های داخلی («سفارش‌های من»، «کدهای تخفیف»، …) پذیرفته نمی‌شوند؛ اگر یک تغییر فیلدی را که قبلاً پر بود (عکس، ساعت کاری، لینک، کارت تماس، موقعیت) بی‌درخواست پاک کند، سیستم خودش آن را برمی‌گرداند.
   **جدول به‌جای متن:** وقتی صاحب کسب‌وکار فهرستی را باید بدهد (منو با قیمت، سؤال‌های آزمون، جلسه‌ها، پرسش‌های متداول، خدمت‌ها)، ایجنت آن را در متن نمی‌پرسد؛ همراه پرسش‌ها یک «کارت جدول» قابل ویرایش در گفت‌وگو نمایش داده می‌شود (ردیف‌های قابل افزودن، جای‌گذاری از Excel، فایل یا عکس برای منو و آزمون، و گزینهٔ «بعداً وارد می‌کنم»). ردیف‌ها در سرور اعتبارسنجی می‌شوند (`app/datasets.py`: قیمت «۷۰ هزار»، گزینه‌ها و افزایش قیمت، روز هفته یا تاریخ شمسی، شمارهٔ پاسخ درست؛ خطا با نام جدول و شمارهٔ ردیف)، به‌صورت جملهٔ دقیق فارسی به مدل داده می‌شوند و **بعد از طراحی، عیناً و بدون دخالت مدل** در بلوک مناسب نوشته می‌شوند؛ پس هیچ قیمت، ساعت یا پاسخی در مسیر گم یا عوض نمی‌شود. واردسازی از فایل از همان کدهای تب «محصولات» و «سؤال‌ها» استفاده می‌کند.
   **اصلاح‌های قطعی بدون مدل:** کد تخفیفِ جایزهٔ آزمون یا دعوت دوستان همیشه خصوصی می‌شود (در دکمهٔ عمومی «کدهای تخفیف» دیده نمی‌شود، وگرنه بدون قبولی هم قابل استفاده بود)؛ ساعت پایان «۲۴» یا «۰۰:۰۰» (بسته‌شدن در نیمه‌شب) آخرین دقیقهٔ همان روز، ۲۳:۵۹، خوانده می‌شود؛ بسته‌شدن بعد از نیمه‌شب (مثلاً تا ۲ بامداد) پشتیبانی نمی‌شود. اگر صاحب کسب‌وکار کارت‌به‌کارت خواسته ولی شمارهٔ کارت نداده، چیزی ساخته نمی‌شود و پیام آخر صریحاً می‌گوید «پرداخت کارت‌به‌کارت اضافه نشد؛ شمارهٔ کارت را بفرستید»، چون ایجنت نباید شماره‌ای از خودش بسازد.
3. **write_tests:** حداکثر چهار سناریو (مراحل با عبارت‌های مورد انتظار/ممنوع، اجرای آماده‌سازی برای ظرفیت، بررسی رکوردها). هر واقعیت مشخصی که صاحب کسب‌وکار داده (نشانی، شماره، ساعت، لینک) باید در یک تست بررسی شود.
4. **run_tests:** اجراکنندهٔ قطعی (`testing.py`) سناریوها را روی موتور اجرا می‌کند و رونوشت گفت‌وگو را ثبت می‌کند (همان چیزی که در تب «تست‌ها» نمایش داده می‌شود).
5. **repair:** تشخیص می‌دهد اشکال از ربات است یا از تست و همان را اصلاح می‌کند؛ تا وقتی تستی رد باشد انتشار قفل می‌ماند.
6. **تغییر (change request):** مدل spec فعلی را می‌گیرد، spec جدید را می‌سازد؛ تفاوت‌ها به زبان ساده نشان داده می‌شود؛ تست‌های قدیمی و جدید دوباره اجرا می‌شوند؛ نسخهٔ جدید ساخته می‌شود و نسخه‌های قبلی قابل مشاهده‌اند.

**کنترل هزینه و پایداری:** هر کاربر ۴۰ اجرا در روز، کل سیستم ۳۰۰ اجرا و ۳۰۰ واردسازی هوشمند در روز؛ سقف درخواست ایجنت در هر پلن (۳۰ تا ۱٬۵۰۰ در ۳۰ روز). اجراهای نیمه‌کاره (مثلاً با ری‌استارت سرور) هنگام راه‌اندازی یا پس از ۶ دقیقه شکست‌خورده علامت می‌خورند تا ربات قفل نماند. هر فراخوانی با تعداد توکن و هزینه در جدول `llm_calls` ثبت می‌شود و قیمت‌ها به صاحب کسب‌وکار نشان داده نمی‌شوند.

**ارزیابی کیفیت ایجنت:** `api/scripts/eval_agent.py` با مدل واقعی ۶۸ مورد را اجرا می‌کند (ساخت‌های پشتیبانی‌شده با بررسی محتوا، ردّ صادقانه‌ی چیزهای غیرممکن، قواعد «هیچ چیز نساز»، و موردهای رگرسیون برای هر خطای گذشته). نتایج و محدودیت‌های اندازه‌گیری در `docs/agent-quality-eval.md` آمده است.

## ۷. منابع داده

- **دیتابیس PostgreSQL** (۴۲ جدول): کاربران؛ ربات‌ها، نسخه‌ها (هر نسخه تغییرناپذیر)، نتایج تست؛ ثبت‌ها (`records`) و نشست مشتری‌ها؛ انتشارها (بله و تلگرام)؛ محصولات و بانک سؤال؛ فایل‌ها؛ اطلاعیه‌ها؛ مشتری‌ها؛ لینک‌های دعوت؛ چت ناشناس؛ صف ارسال پیام؛ اشتراک و پرداخت‌های آزمایشی؛ و `llm_calls` برای هزینه.
- **داده‌ای که صاحب کسب‌وکار می‌دهد:** توضیح ربات، فهرست محصولات (Excel/CSV/متن/عکس/PDF)، سؤال‌های آزمون، عکس‌ها و فایل‌ها.
- **داده‌ای که مشتری می‌دهد:** پاسخ‌هایش در گفت‌وگو (نام، شماره، ثبت‌ها)، متعلق به همان ربات و در دسترس فقط صاحب آن.
- **سرویس‌های بیرونی:** OpenAI (ایجنت، تصویر، embedding)، Bale Bot API، Telegram Bot API (از طریق رله).
- هیچ داده‌ای از شخص ثالث خریداری یا خزیده نمی‌شود.

## ۸. لایهٔ پیام‌رسان و پایداری

**لایهٔ مشترک بله و تلگرام** (`bale.py`): یک مشتری همه‌جا با `bale:<شناسه>` یا `tg:<شناسه>` شناخته می‌شود. ترتیب پردازش هر به‌روزرسانی در یک‌جا ثابت است (تکراری‌ها، پرداخت، گروه/کانال، پیام خصوصی، لینک ربات و دعوت، نشست، قفل عضویت، مسدودی، سقف پلن، موتور، ارسال، ذخیرهٔ نشست) و با قفل هر ربات رقابت روی ظرفیت‌ها ممکن نیست.

**انتشار:** *ربات مشترک بات‌یار* (برای امتحان؛ هر ربات لینک و QR دارد و کسی که بدون لینک بیاید فهرست کسب‌وکارها را می‌بیند) یا *ربات اختصاصی* با توکن خود صاحب کسب‌وکار (رمزنگاری‌شده با کلید مشتق از `JWT_SECRET`، webhook با مسیر مخفی). تبدیل از مشترک به اختصاصی داده‌ها را نگه می‌دارد. تلگرام از طریق رله (`relay/main.ts` روی Deno Deploy) کار می‌کند چون تلگرام از ایران در دسترس نیست.

**قطعی پیام‌رسان‌ها:** `resilience.request()` فقط خطاهای امن را دوباره می‌فرستد (قطع اتصال پیش از ارسال، 429 با احترام به `retry_after`، 502/503/504)؛ خطای «شاید رسیده باشد» هرگز دوباره فرستاده نمی‌شود تا پیام تکراری نرود. سلامت هر پیام‌رسان (`ok / degraded / down`) در پنل به‌صورت نوار هشدار نمایش داده می‌شود. پیام‌های متنی که نرسیده‌اند در صف (`outbox`) با فاصله‌های ۱، ۲، ۴، ۸، ۱۵ دقیقه تا ۵ بار یا ۳۰ دقیقه تکرار می‌شوند و به ترتیب هر گفت‌وگو می‌مانند. webhookها هر ۱۵ دقیقه نوسازی می‌شوند.

**کارهای پس‌زمینه:** یک thread در محیط تولید: یادآوری نوبت، اطلاعیه‌های زمان‌بندی‌شده، انقضای سفارش پرداخت‌نشده، صف چت ناشناس، صف ارسال، نوسازی webhook و پاک‌سازی؛ هر کار جدا از بقیه خطا می‌گیرد.

**پرداخت (فقط بله):** پرداخت آنلاین با فاکتور بله و توکن کیف پول خود صاحب کسب‌وکار (پول مستقیم به کیف پول او می‌رود، نه به بات‌یار). سفارش تا پرداخت در وضعیت «در انتظار پرداخت» با موجودی رزروشده می‌ماند و پس از ۱۵ دقیقه بدون پرداخت لغو می‌شود. کارت‌به‌کارت هم با ثبت رسید و تأیید صاحب کسب‌وکار پشتیبانی می‌شود. پرداخت اشتراک خود بات‌یار در این نسخه **آزمایشی (شبیه‌سازی‌شده)** است و پولی جابه‌جا نمی‌کند.

## ۹. هزینه‌ها

**هزینهٔ هوش مصنوعی (اندازه‌گیری‌شده از لاگ `llm_calls` و مجموعهٔ ارزیابی):**

| مورد | هزینه |
|---|---|
| ساخت یا تغییر یک ربات | حدود ۰٫۰۰۱ تا ۰٫۰۰۹ دلار؛ میانهٔ حدود ۰٫۰۰۲ دلار؛ ۱۲ تا ۴۵ ثانیه |
| اجرای کامل ۶۸ مورد ارزیابی | حدود ۰٫۱۰ دلار |
| هر پیام مشتری | بدون هزینهٔ AI (به‌جز یک embedding حدود ۰٫۰۰۰۰۰۰۳ دلار برای پرسش آزاد در بخش پرسش‌های متداول) |
| واردسازی با عکس/PDF یا ساخت سؤال | چند صدم سنت تا چند سنت بسته به حجم |

**بدترین حالت ماهانهٔ AI برای هر پلن** (اگر کل سقف درخواست ایجنت هر ماه مصرف شود): رایگان ۳۰ × ۰٫۰۰۹ ≈ ۰٫۲۷ دلار، پایه ۰٫۹۰ دلار، حرفه‌ای ۲٫۷۰ دلار، سازمانی ۱۳٫۵۰ دلار.

**میزبانی:** یک نمونهٔ لیارا (پلن small-g2) + دیتابیس PostgreSQL لیارا + رلهٔ Deno Deploy. مبلغ دقیق ماهانهٔ لیارا از پنل لیارا قابل مشاهده است و در بیزینس پلن به‌عنوان هزینهٔ ثابت آمده است. قیمت‌های پلن‌ها پیشنهادی‌اند و هنوز با مشتریان واقعی راستی‌آزمایی نشده‌اند.

## ۱۰. راه‌اندازی و استقرار

**اجرای محلی** (نیازمندی: Python 3.12+ و Node 22+):

```bash
cd api
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
printf 'OPENAI_API_KEY=sk-...\nJWT_SECRET=یک-رشتهٔ-تصادفی-بلند\n' > .env
.venv/bin/uvicorn app.main:app --port 8000
cd .. && ./build.sh        # ساخت رابط کاربری داخل api/static
```

بدون `DATABASE_URL` از SQLite استفاده می‌شود؛ بدون `PUBLIC_BASE_URL` webhookها ثبت نمی‌شوند (شبیه‌ساز وب همه‌جا کار می‌کند). اجرای تست‌ها (با کلید نامعتبر عمداً تا هزینه‌ای ایجاد نشود):

```bash
cd api && OPENAI_API_KEY=sk-invalid DATABASE_URL=sqlite:///./test.db .venv/bin/python -m pytest -q
```

**استقرار روی لیارا:** `./deploy.sh` رابط کاربری را می‌سازد، متغیرهای محیطی را از `api/.env` روی برنامهٔ `botyar` تنظیم می‌کند (بدون چاپ رازها) و تصویر Docker را مستقر می‌کند. لیارا روزانه ۲۰ استقرار مجاز می‌داند.

| متغیر محیطی | کاربرد |
|---|---|
| `DATABASE_URL` | PostgreSQL در تولید |
| `JWT_SECRET` | امضای توکن ورود و کلید رمزنگاری توکن‌های ذخیره‌شده |
| `OPENAI_API_KEY` | ایجنت، تصویر، embedding |
| `BALE_SHARED_BOT_TOKEN` | توکن ربات مشترک `@botyar_ai_bot` |
| `PUBLIC_BASE_URL` | نشانی عمومی برای ثبت webhook |
| `TELEGRAM_RELAY_URL`, `TELEGRAM_RELAY_KEY`, `TELEGRAM_SHARED_BOT_TOKEN` | تلگرام (اختیاری) |
| `BILLING_DEMO` | `true`: ارتقای پلن پرداخت آزمایشی است |

## ۱۱. امنیت

- **ورود:** نام کاربری + گذرواژهٔ هش‌شده، توکن JWT ۷۲ ساعته؛ ۸ ثبت‌نام در ساعت برای هر IP.
- **مالکیت:** هر مسیر `/api/bots/{id}/…` مالکیت را بررسی می‌کند؛ یک تست خودکار همهٔ مسیرها را از OpenAPI می‌شمارد و تأیید می‌کند هر کدام درخواست ناشناس و ربات دیگران را رد می‌کنند.
- **رازها:** توکن ربات و کیف پول رمزنگاری‌شده ذخیره می‌شوند؛ هیچ endpoint رازی برنمی‌گرداند؛ شناسهٔ چت مشتری‌ها در فهرست‌ها دیده نمی‌شود.
- **محدودیت سوءاستفاده:** سقف اجرای ایجنت، سقف پرسش آزاد/چت ناشناس/نظر، سقف اطلاعیه، سقف و بررسی محتوای فایل‌ها (۵ مگابایت، بررسی بایت‌های ابتدایی تصویر، فهرست سفید پسوند)، خنثی‌سازی فرمول در خروجی Excel.
- **جداسازی مشتری:** نشست‌ها به‌ازای ربات و مشتری‌اند؛ دکمهٔ پرداخت آزمایشی فقط در شبیه‌ساز و تست وجود دارد.

## ۱۲. محدودیت‌های فنی (فهرست صادقانه)

1. **یک نمونه:** قفل‌ها و زمان‌بند داخل فرایند هستند؛ برای چند نمونه به قفل دیتابیسی و رهبر برای کارهای پس‌زمینه نیاز است.
2. **آزموده‌نشده روی پیام‌رسان واقعی:** دریافت پست کانال و پیام گروه در بله، فرمت دقیق آپلود چندبخشی فایل، جریان فاکتور، وضعیتی که `getChatMember` برای غیرعضو برمی‌گرداند (قفل عضویت)، مسیر تلگرام (فقط با رلهٔ شبیه‌سازی‌شده آزموده شده). فهرست آزمایش میدانی: `docs/real-bale-checklist.md`.
3. **پرداخت اشتراک بات‌یار آزمایشی است** (درگاه پرداخت متصل نیست).
4. **بازیابی گذرواژه و حذف حساب** وجود ندارد (حساب ایمیل ندارد).
5. **پایش، هشداردهی و پشتیبان‌گیری** فراتر از پیش‌فرض‌های لیارا نداریم.
6. **تست‌ها را همان ایجنتی می‌نویسد که ربات را می‌سازد:** «همهٔ تست‌ها سبزند» یعنی ربات با برداشت ایجنت از درخواست یکی است؛ تأیید نهایی با شبیه‌ساز و صاحب کسب‌وکار است.
7. **ایجنت غیرقطعی است:** گاهی یک مورد باید دوباره امتحان شود؛ حفاظ‌های قطعی (بازگرداندن فیلدهای پاک‌شده، بررسی نام دکمه‌ها، تست واقعیت‌های داده‌شده، اعلان به مدیر برای هر ثبت، کد واقعی برای تخفیف‌های جایزه) این را کم می‌کنند اما صفر نمی‌کنند. نمونه‌های واقعی که با آزمون چندمرحله‌ای پیدا و بسته شدند: ساخت ربات که برای «تا ۲۴» کامل شکست می‌خورد، جایزهٔ دعوت دوستان بدون کد، تغییر عددی که از ۳ به ۵ می‌رفت.
8. **صف پیام:** پیام‌هایی که در قطعی بیش از ۳۰ دقیقه نرسند حذف می‌شوند (عمدی: تأییدیهٔ خیلی دیرهنگام مشتری را گیج می‌کند).
9. **بانک سؤال و جدول محصولات:** فهرست‌ها تا چند صد مورد آزموده شده‌اند، نه هزاران.
10. **چت ناشناس:** مدیریت گزارش‌ها با خود صاحب کسب‌وکار است.
